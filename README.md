# FORMA — демонстрационный сайт мастерской + собственная CRM

**Стек:** HTML / CSS / JavaScript / Supabase (PostgreSQL, Auth, Storage, Edge Functions) / GitHub Pages. Без платных конструкторов и домена.

## Что уже находится в архиве

- `index.html` — адаптивный сайт по утверждённому первому макету FORMA: шапка, главный экран, услуги, три пары «до / после», мастерская, этапы, стоимость, FAQ, заявка, подвал.
- `crm/index.html` — CRM с авторизацией и канбан-доской. Пока конфигурация не заполнена, интерфейс показывает **вымышленные демонстрационные заявки**, ничего не сохраняя.
- `assets/` — логотип и утверждённые визуализации стула, комода и шкафа, основное фото и фото процесса.
- `sql/01_existing_schema.sql`, `sql/02_existing_admin.sql` — ранее выполненные команды (ПОВТОРНО НЕ ЗАПУСКАТЬ).
- `sql/03_lockdown_and_photos.sql` — обязательный следующий SQL: закрывает прямую запись заявок и создаёт частное хранилище фото.
- `supabase/functions/submit-order/index.ts` — серверная функция: принимает форму, проверяет Turnstile, сохраняет фото в приватный Storage и заказ в PostgreSQL.

**Важно:** рабочая отправка заявок с фото включится ТОЛЬКО после настройки Supabase Edge Function и Turnstile. В исходном ZIP сайт сразу открывается визуально, а CRM показывает демонстрационные данные. Мы не выдаём деморежим за настоящую CRM-интеграцию.

## Быстрый просмотр на Windows

1. Распакуй ZIP, не меняя структуру папок.
2. В CMD перейди в папку FORMA: `cd /d "C:\путь\к\FORMA"`.
3. Запусти `py -m http.server 8000` (или `python -m http.server 8000`).
4. Сайт: http://localhost:8000/ ; CRM: http://localhost:8000/crm/ .
5. Завершение сервера: Ctrl+C.

Локальный сервер нужен вместо открытия HTML двойным щелчком, чтобы затем корректно проверять API. Шрифты Google Fonts грузятся из интернета, иначе используются системные аналоги.

## Подключение к существующему Supabase `forma-crm`

1. В **Supabase → SQL Editor → New query** запусти только `sql/03_lockdown_and_photos.sql`. Он удалит ранее разрешённые прямые публичные вставки в `orders`: данные будут поступать только через защищённую функцию.
2. **Supabase → Project Settings → API Keys**: скопируй **публичный publishable key** (или legacy anon key), а URL проекта — из Overview. **Не копируй `service_role` или secret key в файлы сайта.**
3. Создай в Cloudflare бесплатный **Turnstile widget** для адресов `localhost`, `127.0.0.1` и будущего сайта `YOURNAME.github.io` (проверь возможность этих hostnames в текущем интерфейсе Cloudflare). Получишь **site key** и **secret key**.
4. В `js/config.js` заполни `supabaseUrl`, `supabasePublishableKey`, `turnstileSiteKey`. Site key публичный. Убедиcь, что ключи не содержат пробелов.
5. Установи Supabase CLI (подходит `npx supabase --version` при установленном Node.js), выполни `npx supabase login`, затем `npx supabase link --project-ref <PROJECT_REF>` в папке проекта.
6. В Supabase секреты функции должны содержать `TURNSTILE_SECRET_KEY` и `ALLOWED_ORIGINS`. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` обычно предоставляются автоматически в среде Edge Functions Supabase — проверь их наличие в настройках; **не записывай secret key в GitHub или HTML**.

   Пример задания секретов в CMD (выполняй **со своими значениями**, не передавая секреты в переписку):

   ```bat
   npx supabase secrets set TURNSTILE_SECRET_KEY=ВАШ_СЕКРЕТНЫЙ_КЛЮЧ
   npx supabase secrets set ALLOWED_ORIGINS=http://localhost:8000,https://YOURNAME.github.io
   ```

   **Замечание по безопасности:** передавать секрет в командной строке означает, что он может сохраниться в истории/логах. Для более аккуратной настройки используй локальный `.env` (он находится в `.gitignore`) и команду `npx supabase secrets set --env-file .env`.

7. Разверни обработчик: `npx supabase functions deploy submit-order --no-verify-jwt`. Публичный вызов защищён обязательной проверкой Turnstile; это не заменяет ограничения частоты запросов на инфраструктурном уровне.
8. В Supabase Authentication → Users уже создана учётная запись администратора и ранее выполнен `sql/02_existing_admin.sql`. Вход в `/crm/` — по email и паролю **пользователя Authentication**, не паролю от базы данных.
9. Тест: отправь **тестовую** заявку с одним изображением → открой CRM, войди → проверь карточку и фото → измени статус/стоимость → обнови страницу.

### Обязательная настройка перед публикацией

- Обнови `privacy.html`: сейчас там **шаблонное предупреждение**, а не полноценная политика конкретного оператора данных. До этого не предлагай реальным людям отправлять личные данные.
- Форма должна принимать только тестовые данные, пока не проверена законность обработки и безопасность.
- Если сайт на GitHub Pages будет опубликован по `https://YOURNAME.github.io/forma/`, значение `ALLOWED_ORIGINS` равно `https://YOURNAME.github.io` **без пути**.
- Edge Function вызывается по URL Supabase, GitHub Pages ничего не знает о серверных секретах.
- Используй отдельного администратора и сильный пароль. Не показывай реальные заявки в Kwork, только демоданные.
- Free Supabase может приостанавливать неактивные проекты. Для публичного портфолио периодически проверяй доступность.

## Публикация без домена

После локальной проверки создай **публичный** репозиторий `forma`, загрузи содержимое папки, в Settings → Pages выбери Deploy from a branch → `main` → `/ (root)`. Сайт появится по `https://YOURNAME.github.io/forma/`, CRM — `https://YOURNAME.github.io/forma/crm/`. **Исходный код публичный**, поэтому никакие секретные значения в него не помещаем. `noindex` в CRM — лишь просьба поисковикам, реальную защиту обеспечивает Supabase Auth + RLS.

## Ограничения и коммерческий статус

Это демонстрационный кейс, не сайт действующей мастерской. Фото «до/после» — сгенерированные концептуальные визуализации. Цены ориентировочные и не являются офертой. Конкретные юридические данные, адрес и контактные реквизиты намеренно не придуманы. Тексты, логотип и реальные фотографии можно заменить при адаптации к заказчику.
